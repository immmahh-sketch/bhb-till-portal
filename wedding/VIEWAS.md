# "View as the couple": a safe test copy of a couple's Wedding App

The back office can open any couple's real Wedding App on screen and click through every feature to see what the couple sees and to try things out. Nothing done there is saved, emailed or paid. Two layers keep it safe:

1. **The server refuses everything that is not a read.** `wedding-admin` action `viewas.open` { id: weddingId, staff_email } -> `{ token, wedding, staff:true, sandbox:true }` (wedding = the same shape `wedding-login` returns). The token is a normal Wedding App session token marked as a test session (8 hours). With it `wedding-api` answers ONLY these actions: `dashboard, guests.list, tables.list, menu.list, suppliers.list, budget.list, photos.list, photos.download, foodsheet, chat.list, chat.unread, teamphotos.list`. Every other `wedding-api` action returns HTTP 403 `{ error:"This is the test view, so that was not saved.", code:"SANDBOX" }`. `send-guest-invite` answers only `action:"preview"` (anything else: 403 SANDBOX "nothing was sent"); `sumup-create-wedding-checkout` and `journal-scan` always return 403 SANDBOX. `chat.list` never marks anything read for a test session.
2. **The app simulates changes on the page** so the features feel real. This is the client's job (below). The server refusal is only the safety net: the page must not even try to send a write.

## The app (`wedding/index.html`)
* Opens with `wedding/index.html#viewas=<token>` (the page is shown in an iframe in the back office, or in its own tab). On boot, if the hash has `viewas=`: take the token, immediately remove it from the address (`history.replaceState`), use it as the session (no login screen), load the app exactly as for the couple, and set `S.sandbox = true`. A page reload inside the test view must not need the hash again (keep the token in `sessionStorage` under a test-only key and never in the couple's normal session key, so a test view can never become a real login).
* A calm banner at the top (replacing the "Back office view" bar): "Test view of <salutation> (<event ref>). Nothing you do here is saved, sent or paid." with **Reset** (clears every simulated change and reloads the data) and a note "Closing this window resets everything".
* **Sandbox data layer:** in test mode every `callFn("wedding-api", ...)` goes through an in-memory fake of the wedding-api lists. First read of each list comes from the real server (allowed); the result is cached in memory and every later read AND every write is served from that cache: `guests.save/delete/bulk/markRsvp`, `tables.save/delete/setup/assign/assignMany`, `suppliers.save/delete`, `budget.save/delete/setTotal/syncVenue`, `progress.toggle/removeCustom`, `invite.settings`, `photos.update/delete/settings`, `chat.send`, `teamphotos.start/save/caption/delete`. Server-assigned ids are replaced by locally made ones. `dashboard` stays real but its progress, budget total, invitation settings and anything else the app derives from those writes is patched from the cache so the home view, checklist, budget and invite preview agree with what the tester did. Photo uploads use local object URLs instead of uploading. `chat.send` appends a local couple message (with a small "test message, not sent" marker); no team reply arrives.
* Other functions in test mode: `send-guest-invite` `preview` is real; any send is simulated: report success with the number of guests it WOULD have emailed and say clearly "Test view: no emails were sent". `sumup-create-wedding-checkout`: do not call it; show a calm dialog "Payments are switched off in the test view. This is where the couple would be taken to the card payment page." `journal-scan`: do not call it; show "Scanning is switched off in the test view." `wedding-login`/session refresh: never.
* The existing staff read-only branches added earlier for chat and photos ("Back office view, read only") must apply only to a real staff session (`staff && !sandbox`); in the test view those features are fully usable (simulated).
* The back-office "Back office view" bar for normal staff sessions (`staff && !sandbox`) stays as it is.
* Resilience: if any request in test mode returns 403 `SANDBOX` (a path the simulation missed), do not show a scary error: show a small notice "Test view: that action is not saved" and carry on; and log the action name to the console so it can be added to the simulation.

## The back office (`wedding-admin.html`)
* On a wedding's page: a button **View as the couple** (and a small link on the Weddings list rows, if easy). It calls `viewas.open` (include `staff_email`), then shows a large overlay panel containing the Wedding App in an iframe (`wedding/index.html#viewas=<token>`, same site so a relative URL works) inside a phone-shaped frame, with: device buttons (Phone 390 wide / Tablet 768 / Desktop 1100, iframe height fills the screen), **Reload** (resets the test), **Open in a new tab**, **Close**, and a line: "Test view of <couple>. You see exactly what they see. Anything that would save, send an email or take a payment is only simulated here, and everything resets when you close this."
* Refuse to open for an "event" account with no app (the server returns 404 with a message; show it).
